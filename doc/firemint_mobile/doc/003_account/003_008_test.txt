
Account 実機テスト手順書

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

003_006/003_007で見つけた12件の修正と、003_003「実機テストの確認状況」の
未確認分をあわせて検証する。Playストア（Internal testing）経由でのインストールが前提。

各項目は、確認するポイントを3つに分けて書く。
・【Firebase Auth】… Authenticationのユーザー一覧で見るポイント（件数・uid・表示ラベル）
・【Firestore】　　… コレクション/ドキュメント/フィールドの中身（作成・更新・削除）
・【端末】　　　　… アプリ画面の見た目・遷移・ダイアログ




================================================================================
用語（テスト中に混同したため、必ず先に確認する）
================================================================================

ホーム画面には、似て非なる2つの入口がある。

・「認証」　　＝　firestoreアカウント　＝　`connectWithGoogle`（connection機能）。
　　　　　　　　　外部Firestoreプロジェクトへの接続用。Firebase Authには一切触れない。
　　　　　　　　　【E章以外ではこのテスト手順書の対象外】。押さないこと。

・「アカウント」＝ firemintアカウント　＝ `AccountScreen`（account機能）。
　　　　　　　　　課金・トライアル・メンバー管理はすべてここ。中の「Googleでログイン」
　　　　　　　　　ボタンだけが、実際にFirebase Authにgoogleアカウントを結び付ける。
　　　　　　　　　【このテスト手順書は、基本的にすべてこちらを対象にする】。

以降、このテスト手順書で単に「アカウント画面」「ログイン」と書いた場合は、すべて
「アカウント」（firemintアカウント）側を指す。

（ホーム画面のカード並び順は、混同を防ぐため「アカウント」を左上に変更済み。
　003_002_flow.txt「利用状態の判定」参照）




================================================================================
前提（テスト環境）
================================================================================

・Googleアカウントを2つ用意する（A = owner役、B = サブ垢役）。もう1つ（C = 別owner役）
　もB5で使うので、可能なら3つ目も用意する。全員Play Consoleの「ライセンステスター」に
　登録しておく（本当に課金されるのを防ぐ）。
・versionCodeを上げてアップロードし、Internal testingのテスターとしてPlayストア経由で
　インストールする（adb installでは購入・招待どちらも正しく検証できない）。
・ログの確認: `firebase functions:log`（全体）、`firebase functions:log --only androidRtdnWebhook`
　のように関数名で絞り込める。
・テスト購入のサブスクは、実際の1ヶ月ではなく約5分ごとに自動更新され、購入から約35分で
　期限切れになる（003_003_misc.txt参照）。更新・期限切れ絡みのテストはこれを利用する。
・破壊的な操作（データ削除）は必ず最後に行う。実行するとテストデータが消える。
・Firestoreの中身は、Firebaseコンソールから直接確認できる（users / accounts / members /
　subscriptions の各コレクション）。「思った通りの画面表示か」だけでなく、
　「Firestoreの中身が思った通りか」もあわせて見ること。
・各項目のuid・accountId・ドキュメントの値は、その場でメモを取りながら進めること
　（後の項目で「前と同じか」「前と違うか」の比較に必要）。




================================================================================
A. 起動・トライアル基本（003_011_device.txt）
================================================================================

　※ devices のドキュメントIDは、Android ID の SHA-256。コンソールで探す時は、
　　users/{uid}/devices の中のドキュメントIDを見る（同じ値）。
　※ この端末の firstUseDate は、アプリが SQLite に写して使う。日常の起動では、サーバーに聞かない。
　　コンソールで devices/{deviceIdHash}.firstUseDate を書き換えてテストする時は、書き換えた後に
　　アプリのデータを消去して（または再インストールして）起動する。

A1. 起動しただけで、この端末のトライアルが始まる
　手順: 初回インストール後、「アカウント」画面を開かずにアプリを起動するだけ
　【Firebase Auth】
　　・ユーザーが1件増える。プロバイダ欄は人型アイコン、IDは「（匿名）」
　　・このuidを控えておく
　【Firestore】
　　・users/{そのuid} が作られる（email="", name="", platform="android", accountId=null）
　　・users/{そのuid}/devices/{deviceIdHash} が作られる
　　・devices/{deviceIdHash} が作られる（firstUseDate=起動時刻に近いサーバー時刻。expireAt は無い）
　【端末】
　　・「アカウント」画面を開くと、Authenticationで控えたuidと同じuidが表示される
　　・「この端末のトライアル 残り60日」の表示になる

    → OK



A2. 匿名のまま再インストール → トライアルが続く
　前提: A1の状態。devices/{deviceIdHash}.firstUseDate をメモしておく
　手順: アンインストール → 再インストール → 起動
　【Firebase Auth】
　　・A1の匿名ユーザーが消え、新しい匿名ユーザーが1件できる（uidは変わる。件数は増えない）
　【Firestore】
　　・devices/{deviceIdHash} は同じ1件のまま。firstUseDate が変わっていない
　　・users/{A1のuid} と、その下の devices が消える
　　・users/{新しいuid} と users/{新しいuid}/devices/{deviceIdHash} が作られる
　【端末】
　　・トライアル残り日数が、連続した日数のまま（60日に戻らない）

    → OK



A3. Googleログイン済みで再インストール → ログインで元の契約に戻る
　登場するもの: 端末1台、Googleアカウント A
　前提: この端末で、既に A でログインしてある（サーバーに、Aのuid と account がある）。
　　　　このuid・accountIdを、アンインストール前にメモしておく
　手順:
　　1. アンインストール → 再インストール → アプリを起動する
　　　 （端末のログイン状態だけが消える。サーバーの Aのuid は残る）
　　2. 「アカウント」画面を開き、uidを確認する（新しい匿名uid になっている）
　　3. 「アカウント」画面で「Googleでログイン」→ Aでログインする（Aでのログインは2回目）
　【Firebase Auth】
　　・手順2の時点: 2件（前提の Aのuid と、手順1でできた新しい匿名uid）
　　・手順3の後: 1件に戻る。匿名uidは消え、端末は Aのuid に切り替わる。
　　　残るのは、メモしたAのuid
　【Firestore】
　　・手順2の時点: users/{匿名uid} が作られる。users/{Aのuid} は残っている
　　・手順3の後: users/{匿名uid} と、その下の devices が消える。
　　　users/{Aのuid}.accountId は、メモした値のまま
　　・devices/{deviceIdHash}.firstUseDate は、最初から最後まで変わらない
　【端末】
　　・手順2の時点: 匿名。トライアル残り日数は、再インストール前から連続している
　　・手順3の後: Aのメールアドレスが表示され、元の契約状態に戻る。
　　　トライアル残り日数は変わらない

    → OK



A4. 1つのGoogleで複数端末 → 同じ契約。トライアルは端末ごと
　手順: 端末1の「アカウント」画面でAログイン → 端末2の「アカウント」画面でAログイン
　【Firebase Auth】
　　・端末1・端末2とも、同じ1件（同じuid）
　【Firestore】
　　・users/{Aのuid}/devices に、2件ある（端末1と端末2）
　　・devices に、端末1と端末2の2件がある。firstUseDate は、それぞれの端末で
　　　初めて起動した日時
　【端末】
　　・両端末で、同じ契約状態（契約中なら、どちらも契約中）
　　・トライアル残り日数は、端末ごとに違う（それぞれの devices の firstUseDate から数える）

    → OK





================================================================================
B. 匿名→Google認証・合流（joinAccount / respondToInviteの書き直し）
================================================================================
　※ここでいう「Google認証」「ログイン」は、すべて「アカウント」画面の中の
　　「Googleでログイン」ボタンのこと。

B1. 通常の昇格（招待なし）
　前提: 匿名のまま（まだGoogleログインしていない）
　手順: 「アカウント」画面で「Googleでログイン」→ A
　【Firebase Auth】
　　・uidは変わらない（匿名の時と同じ）。プロバイダにGoogleが追加され、
　　　IDにAのメールアドレスが表示されるようになる
　【Firestore】
　　・users/{同じuid}.email/nameが、Aのメール・表示名に更新される
　　・accounts/{新しいaccountId} が新規作成される（createdAt, ownerUid=このuid）
　　・accounts/{accountId}/members/{同じuid} が作成される（email, addedAt）
　　・users/{同じuid}.accountId が、この新しいaccountIdに更新される
　【端末】
　　・確認ダイアログ（招待の確認）は出ない
　　・「アカウント」画面にAのメールアドレスが表示される
　　・トライアル残り日数はそのまま（昇格では、この端末の日付は変わらない）
　　・購入ボタンが表示される（ownerなので）

    →　OK



B2. 招待を受けて参加する
　前提: Aのaccountに、addMemberでBのemailを仮登録済み（members/{Bのemail}が存在）
　手順: Bの端末の「アカウント」画面で、初めてBでログイン
　【Firebase Auth】
　　・Bのuidは変わらない。プロバイダにGoogleが追加され、Bのメールアドレスが表示される
　【Firestore】
　　・「参加する」を押す前: 何も変わらない
　　・「参加する」を押した後: accounts/{Aのaccount}/members/{Bのemail} が削除され、
　　　代わりに members/{Bのuid} が作られる（emailは保持、addedAtは元の招待日時を引き継ぐ）
　　・users/{Bのuid}.accountId が、Aのaccountidに更新される
　【端末】
　　・「Aさんのfiremintに参加しますか？」の確認ダイアログが表示される
　　・「参加する」を選ぶと、Bの「アカウント」画面がAのaccountの契約状態
　　　（トライアル or 契約中）を表示するようになる
　　・Aの「アカウント」画面を開き直すと、メンバー一覧にA・Bが並ぶ

    →　OK



B3. 招待を辞退する
　前提: B2と同じ状況を作り直す（Aが再度addMemberでBを招待）
　手順: Bでログイン → 確認ダイアログで「参加しない」を選択
　【Firebase Auth】変化なし
　【Firestore】
　　・accounts/{Aのaccount}/members/{Bのemail} が削除される（uidへの差し替えは
　　　起きない）
　　・Bのusers/{Bのuid}.accountIdは、同じログイン処理の中でそのまま更新される
　　　（下記参照。「招待前の状態のまま」ではない）
　【端末】
　　・この手順（ログイン時に辞退）は、AccountScreen.tsxのonLinkGoogle→
　　　joinOrCreateAccountを経由する。respondToInviteがjoined:falseを返した後、
　　　existingAccountIdも無い（Bは初回ログインのため）ので、その場で続けて
　　　createAccount()が呼ばれ、同じログイン操作の中でBが自分だけのownerになる
　　　（次回起動やフォアグラウンド復帰を待たない。即時）
　　・Bの契約状態は、辞退直後から自分の新しいaccount（トライアルのみ）の表示になる

　　※ 似て非なる別シナリオ（InviteWatcher経由の辞退）:
　　　既にログイン済みのBが、後から招待され、フォアグラウンド復帰時に
　　　InviteWatcher.tsxの確認ダイアログで「参加しない」を選んだ場合は、
　　　respondToInviteがjoined:falseを返しても、InviteWatcher.tsx側は
　　　createAccountを呼ばない。この場合だけ、Bのaccountidは招待前の状態の
　　　まま持ち越され、次回起動かフォアグラウンド復帰時のcheckForInviteで
　　　（pendingInviteが既に消えているため）自動作成の分岐に入る。
　　　この手順書のB3はこちらではない（上記の即時作成のケースを指す）。

    →　OK



B4. 課金中は確認すら出ずに拒否される
　前提: Bが自分のaccountで既に課金中（D2を先に実施しておく）
　手順: Aが（別の）accountからBのemailをaddMember → Bでアプリを開く
　【Firebase Auth】変化なし
　【Firestore】
　　・accounts/{Aのaccount}/members/{Bのemail}（新しい招待）が、確認を経ずに
　　　削除される
　【端末】
　　・確認ダイアログもエラーも出ない。Bの画面は何も変化しない

    →　OK



B5. 既に所属中の人が、別のaccountから招待される（今回の修正の本丸）
　前提: BはAのaccountに所属済み（B2で参加済み）。owner Cが、別のaccountで
　　　　改めてBのemailでaddMemberする
　手順: Bでアプリを起動（またはフォアグラウンド復帰）
　【Firebase Auth】変化なし
　【Firestore】
　　・accounts/{Aのaccount}/members/{Bのuid} が削除される
　　・accounts/{Cのaccount}/members/{Bのuid} が新規作成される
　　・users/{Bのuid}.accountId が、CのaccountIdに更新される
　　・Aのaccount本体・subscriptions・他member（Aのエントリ）には変化なし
　【端末】
　　・「Cさんのfiremintに参加しますか？」の確認ダイアログが出る（Bが既にAの
　　　accountに所属していることに引きずられて、この招待が無視されないこと）
　　・「参加する」後、Bの契約状態表示がCのaccountの状態に変わる
　　・Aの「アカウント」画面を開き直すと、メンバー一覧からBが消えている





B6. 招待チェックがアプリ起動のたびに動く（InviteWatcher）
　前提: Bはログイン済み。Aが新たにBのemailをaddMemberする
　手順: Bはアプリを起動し直さず、いったんバックグラウンドに回してから、
　　　　フォアグラウンドに戻す（アプリを切り替えて戻ってくるだけでよい）
　【Firebase Auth】変化なし
　【Firestore】変化なし（この時点ではまだ確認前のため）
　【端末】
　　・アプリを開き直さなくても、フォアグラウンド復帰のタイミングで確認ダイアログが出る

    →　NG



B7. アカウント画面を開いただけで招待の確認が出る
　前提: Bはログイン済みで、自分のaccountを持っている。Aが新たにBのemailをaddMemberする
　手順: Bはアプリをバックグラウンドに回さず、ホーム → 「アカウント」画面を開く
　【Firebase Auth】変化なし
　【Firestore】
　　・「参加する」を押す前: 何も変わらない
　　・「参加する」後: B2と同じ（members/{Bのemail}→members/{Bのuid}、users/{Bのuid}.accountId
　　　がAのaccountIdに）
　【端末】
　　・アカウント画面は先に表示され、少し遅れて確認ダイアログが出る
　　・「参加する」後、同じ画面のまま、Aのaccountの契約状態・メンバー一覧に切り替わる
　　・ダイアログの外側タップ・戻るボタンでは閉じない（どちらかを選ぶまで残る）
　追加: アプリ起動直後にすぐ「アカウント」画面を開いても、確認ダイアログは1つしか出ない

    →　OK

C. メンバー一覧・脱退（owner操作 / 自己脱退）
================================================================================
　※すべて「アカウント」画面の中の操作。

C1. メンバー一覧の表示
　前提: Aのaccountに、Bがmemberとして参加済み
　手順: Aの「アカウント」画面を開く
　【Firebase Auth】変化なし（読み取りのみ）
　【Firestore】変化なし（読み取りのみ）
　【端末】
　　・「メンバー」欄に、自分（A、「(あなた)」表記）とB（emailが表示される）が並ぶ
　　・Bの行にだけ「外す」ボタンが出る（Aの行には出ない）

    →　OK



C2. owner操作でメンバーを脱退させる
　手順: C1の状態で、Aが「外す」を押してBを脱退させる
　【Firebase Auth】
　　・Bのユーザーは削除されない（残る）
　【Firestore】
　　・accounts/{Aのaccount}/members/{Bのuid} が削除される
　　・users/{Bのuid}.accountId が null になる（users自体は削除されない）
　【端末】
　　・Aのメンバー一覧からBが消える
　　・Bの端末で「アカウント」画面を開き直すと、契約状態がtrialのみの判定に
　　　切り替わっている（その端末のfirstUseDateが60日以内ならtrial、超えていればexpired）

    →　OK



C3. 自己脱退（member自身）
　前提: BがAのaccountに参加し直した状態（addMember → B側で参加）
　手順: Bの「アカウント」画面で、「このグループから脱退する」を押す
　【Firebase Auth】変化なし（Bのユーザーは残る）
　【Firestore】C2と同じ結果（members/{Bのuid}削除、users/{Bのuid}.accountId=null）
　【端末】
　　・確認ダイアログの文言が、Bの端末のfirstUseDateが60日を超えているかどうかで
　　　出し分けられている（「もし終了していたら」の条件文 or 断定形の文言）
　　・確定するとBはaccountから抜け、A側の画面（開き直すと）でもBが消えている

    →　OK



C4. owner自身は「外す」対象にならない
　手順: Aのメンバー一覧で、自分（owner）の行を確認する
　【端末】
　　・自分の行には「外す」ボタンが表示されない（owner自身が抜ける場合は「データ削除」）

    →　OK

D. Androidで課金
================================================================================
　※すべて「アカウント」画面の中の操作。

D1. 購入ボタンはownerにしか出ない
　前提: BがAのaccountのmemberとして参加済み
　手順: A・Bそれぞれの「アカウント」画面を開く
　【端末】
　　・Aには購入ボタンが出る。Bには出ない
　　・「メンバーを追加」欄は、Bには表示されない
　　・Bには代わりに「このグループから脱退する」が出る

    →　OK



　追加:
　　・A・B・匿名ユーザーのどれにも、「データ削除」のボタンが1つだけ出る
　　　（「退会」「自分のデータを削除」というボタンは無い。P1で確認する）

    →　



D2. 通常の購入
　手順: Aが購入ボタンから、テスト購入する
　【Firebase Auth】変化なし
　【Firestore】
　　・subscriptions/{purchaseToken} が新規作成される
　　・accountId=Aのaccountid, provider="Google Play", purchaseToken, productId,
　　　expiryTime（現在から約5分後）, lastNotificationType, createdAt, updatedAt
　【端末】
　　・検証成功後、「契約中」表示になる

    →　OK



D3. 自動更新とRTDN反映
　手順: D2のまま、5分ごとの自動更新を数回まつ（ログで確認: androidRtdnWebhook）
　【Firestore】
　　・同じsubscriptions/{purchaseToken}のexpiryTime・updatedAt・lastNotificationType
　　　だけが更新される（新しいドキュメントは増えない。件数を確認する）
　【ログ】
　　・`firebase functions:log --only androidRtdnWebhook`に「RTDNを反映しました」
　　　が、更新のたびに出る
　【端末】
　　・約35分後、期限切れになり「トライアル + 購入ボタン」に戻る
　　・Bの画面がある場合、Bの契約状態もこのaccountの状態に連動して変わる

    →　OK



D4. 猶予期間（IN_GRACE_PERIOD）の扱い
　手順: 支払い方法のエラーなど、猶予期間に入る状況を作れる場合は試す（難しければ省略可）
　【Firestore】
　　・lastNotificationType が "IN_GRACE_PERIOD" になる（通知の名前ではなく、
　　　Play APIの今の状態から決めた名前）。expiryTimeは過去のままでもよい
　【端末】
　　・expiryTimeが過去でも「契約中」表示のまま（isGracePeriodの判定）

    →　skip



D5. REVOKED（返金・取り消し）で即座に無効化される
　手順: テスト購入を、Google Playの購入履歴から払い戻す（できない場合はログで代用）
　【Firestore】
　　・subscriptions/{purchaseToken}.expiryTime が、Play側の値を待たずに
　　　【現在時刻】に強制更新される
　　・lastNotificationType が "SUBSCRIPTION_REVOKED" または
　　　"VOIDED_FULL_REFUND"（もしくは"VOIDED_PARTIAL_REFUND"）になる
　【端末】
　　・即座に「契約中」ではなくなる（Play側の再取得結果を待たない）

    →　



D6. 購入の復元
　手順: D2の状態でアンインストール → 再インストール → 「アカウント」画面でAログイン
　　　　→ 購入ボタンを押す
　【Firestore】

S. firestoreアカウントの切り替えと、アカウントごとのプロジェクト一覧
================================================================================
　※ この章だけは、「認証」（firestoreアカウント。外部Firestoreへの接続）側の操作。
　　「アカウント」（firemintアカウント）側は触らない。冒頭の「用語」を参照。
　変更点:
　・プロジェクトの登録（端末のSQLite）を、firestoreアカウントごとに持つ。
　　プロジェクト一覧と、インポート/エクスポートのプロジェクト選択には、いまのアカウントの分だけが並ぶ。
　・同じプロジェクトIDを、アカウントごとに別々に登録できる。
　・プロジェクト一覧に、いまのアカウントのメールアドレスを出す。
　　その下に「アカウント切り替え」と「サインアウト」を並べる（タイトルのすぐ下の、1つの枠の中）。

　・「プロジェクト一覧」「認証」「インポート/エクスポート」の3つのカードとも、入口でサインインを済ませる。
　・トークンは、サインイン中のアカウントを指定して取る（GoogleAuthModule.kt）。

　【端末】

　　・手順5: 保存すると、「先に Google 認証してください」と出る。登録されない
