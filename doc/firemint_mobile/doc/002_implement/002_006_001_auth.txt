================================================================================
概要
================================================================================


＊　対象プロジェクトの Firebase Auth ユーザー（そのプロジェクトのアプリを使う
　　エンドユーザー）を、一覧・編集・削除（単発）・書き出し。

＊　IAM（プロジェクトの権限保持者）ではない。混同しない。

＊　複数一括（一括削除・一括無効化）はやらない。1 件ずつ操作する。

＊　無効化/有効化（disabled の切替）は「保存」に含めない。単独の確認付き操作。
　　トグル1つの操作で即ログイン不可になる、削除と同じくらい重い処理として扱う。

＊　スコープは datastore とは別（identitytoolkit）。002_006_002 で別申請する。
　　Firestore の実処理と混ぜない。android/auth_users を別に持つ。


================================================================================
UI
================================================================================


入口:
  プロジェクト一覧 → プロジェクトを選ぶ
    → コレクション一覧（CollectionListScreen）の、コレクション一覧の
      一番下、区切り（ブランク＋線）を挟んで「AUTH」を1項目として置く。
      タイトル行（プロジェクト名 + ＋追加）の下ではない。コレクション一覧が
      主役のまま、Auth はその他扱いで最下段。
      コレクション数が多いプロジェクトではスクロールが必要になるが、
      使用頻度が低い機能なので想定通り。
  本家のように左右分割は無し。モバイルは explorer と同じ「一覧 → 詳細」。


潜る:
  Auth ユーザー一覧
    → ユーザー詳細（編集）


一覧画面:
  ・検索（uid / email / displayName / phoneNumber の部分一致。取得済み分のみ、
    サーバーに問い合わせ直さない）
  ・行: email（無ければ uid）、状態（active / disabled）、lastSignInTime
  ・ページング: 続きを読む（本家と同じ、maxResults 100 ずつ）
  ・タップでユーザー詳細へ


ユーザー詳細（編集）画面:

  編集フォーム（1つの保存ボタンでまとめて送信）:
    ・uid（表示のみ）
    ・email
    ・displayName
    ・phoneNumber
    ・password（新しいものを入れたときだけ変更。空なら変更なし）
    ・emailVerified（トグル。これは軽い＝保存ボタンに含めてよい）
    ・customClaims（JSON テキスト。パース失敗は保存させない）
    ・保存ボタン

  単独の操作（編集フォームの外。それぞれ確認ダイアログ1回 → 実行/キャンセル）:
    ・無効化する／有効化する ボタン（今の disabled の逆を表示。押した瞬間に
      confirmWrite で「このユーザーは今すぐログインできなくなります。
      よろしいですか？」（有効化なら「今すぐログインできるようになります」）
      → 確定したら即 API 呼び出し。保存ボタンの入力内容とは無関係に、
      その場で反映する
    ・削除ボタン（単発。confirmWrite で「このユーザーを削除しますか？
      取り消せません」→実行/キャンセル）


書き出し:
  ・一覧画面のヘッダーに JSON / CSV ボタン
  ・対象は「今読み込み済みの全件」（ページング途中なら、その時点の件数のみ）
  ・保存先は、押すたびに、端末のファイル選択の画面（SAF）で選ぶ。
    既定の保存フォルダへの保存は、作らない（決定。data_transfer とは揃えない）


================================================================================
詳細
================================================================================


＊　read-only プロジェクト
　　一覧・詳細の閲覧はできる。保存・削除はできない（assertWritable と同じ扱い）。


＊　対象プロジェクトごとの Identity Toolkit API 有効化 → アプリから自動化する
　　firemint-m の Google 申請（002_006_002）とは別の話だが、対処はアプリに含める。
　　対象プロジェクト（bluepenguin 等）ごとに、そのプロジェクトの編集権限を持つ人が
　　identitytoolkit.googleapis.com を一度だけ有効化する必要がある問題そのものは残る
　　（Firebase Authentication をコンソール/公式SDKで使っているだけでは有効にならない。
　　公式SDKは別経路でアクセスするため）。

　　cloud-platform は取らない（002_006_002「やらない」）。代わりに
　　service.management（Google API のサービス設定を管理するだけの狭いスコープ。
　　Firestore・Cloud Storage 等のデータには触れない）を追加で申請し、
　　Service Usage API の services.enable をアプリから直接呼んで、
　　その場で identitytoolkit.googleapis.com を有効化できるようにする。

　　UI: 一覧の読み込みが API_DISABLED で失敗したとき、今まで通りエラーの説明を
　　画面内に表示しつつ、「有効化する」ボタンを追加する。押すと
　　service.management のトークンを取得 → services.enable を呼ぶ → 成功したら
　　自動でもう一度一覧を読み込む。ブラウザに出て手動で有効化ボタンを押す手間を無くす。
　　有効化リンクを開くリンクは（ブラウザ側でも確認したい場合のために）残す。


＊　customClaims
　　JSON オブジェクトのみ許可。配列・null 直書き・壊れた JSON は保存前に弾く。
　　空 `{}` は「クリア」ではなく「空オブジェクトを設定」。全クリアしたいときの
　　挙動は本家に合わせて null 送信にするか要検討（本家: customClaims が undefined
　　なら変更なし、null なら全クリア。モバイルの JSON テキスト欄は「空文字＝{}」
　　として扱い、null 送信の UI は作らない）。


＊　password
　　新しい値を入れて保存したときだけ更新。表示は常に空欄（既存値は取得できない
　　し、そもそもFirebase Auth は平文パスワードを返さない）。


＊　削除の確認文言
　　「このユーザーを削除しますか？取り消せません」。confirmWrite を通す。
　　削除後は一覧に戻る。一覧は読み直さず、削除したユーザーの行だけを消す
　　（保存・無効化/有効化の後も同じ。その行だけを、変えた後の値に差し替える）。


＊　無効化/有効化
　　保存ボタン（他フィールドの一括保存）には含めない。専用ボタン＋confirmWrite
　　1回で確定、その場で API 呼び出し。他の未保存の編集（email 等の入力途中）が
　　あっても、無効化/有効化の実行には影響しない・巻き込まない。
　　実行後は詳細画面の表示（状態）を更新する。


＊　一覧の検索は端末内メモリでの絞り込みのみ。サーバー側の検索 API は無い
　　（Firebase Auth の listUsers 自体に検索条件は無い）。

　　（ユーザーが必要な分だけ読み込む）。


□ providerIds の表示
→　一覧には出さない（狭い）。詳細画面に表示。
