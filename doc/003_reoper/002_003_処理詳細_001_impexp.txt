動きがモバイル版と違うもの
================================================================================


＊　追記の書き方
    今   1 件ずつ get() で確かめてから batch.create（write_dump.ts の writeDocuments）。
         確かめてから書くまでの間に同じドキュメントができると、バッチがまるごと失敗する。
    直す まとめて書き、既にあるもので断られたもの（ALREADY_EXISTS）を、飛ばした件数として数える。
         1 件ずつ get() で確かめない。

＊　ファイルの中で同じパスが 2 回以上出てきた時
    今   どちらも「無い」と判断されて同じバッチに入り、バッチが失敗する。
    直す 最初の行だけを書く。2 回目以降は書かずに、飛ばした件数として数える。

＊　メモリの使い方
    今   インポートは、ダンプ全体をメモリに読んでから書く（readOfficialDump が配列を返す）。
         エクスポートは、全件をメモリに集めてから書き出す（collectDocuments）。
    直す インポートは、1 回目に件数を数え、2 回目に書く。
         エクスポートは、1 ページ読むたびにファイルへ書き足す。

＊　結果
    今   書いた件数 / 飛ばした件数 / 衝突したパスの例
    直す 書いた件数 / 飛ばした件数 / 書けなかった件数 / 途中で止まった理由

＊　保存先
    今   毎回、保存ダイアログを出す。
    直す 画面に保存先を出す。選ばない時は Documents/FireMint に、自動の名前
         （export-{範囲}-{名前}-{時刻}.zip / .jsonl）で保存する。
         「保存先を選ぶ…」は、場所とファイル名を一緒に選ぶダイアログ（OS の保存ダイアログ。ボタンは「選択」）。
         「選択」を押した時は保存しない。保存するのはエクスポートの時。
         ダイアログの最初の値は、前に選んだフォルダ（無ければ Documents/FireMint）と自動の名前。
         同じ名前のファイルを選んだ時は、OS が上書きを確かめる。
         選んだフォルダは、エクスポートの後も、形式・範囲を変えても残る。
         選んだファイル名は、エクスポートを始めた後は自動の名前に戻る。形式を変えると拡張子も変わる。

＊　書きかけのファイル
    今   作業用の一時フォルダは消すが、zip を書く途中で失敗した時、出力先の zip を消さない。
    直す 途中で止まった・中止した・中身が無かった時は、書きかけのファイルを消す。



================================================================================
検証
================================================================================


＊　インポートだけ。書き込みなし（dry run）。
    任意。押さなくても実行できる。
    検証なしで実行する時は、検証していないと警告する。警告のあと実行できる。
    read-only のプロジェクトでも検証はできる（実行はできない）。
    shared/safety の確認は、実行だけに通す。検証は通さない。

＊　簡易と詳細
    簡易  コレクション ID ごとの件数（クラウド / ファイル）
    詳細  簡易に加えて、側ごとの差分ドキュメント数と、中身が違うドキュメントの数

＊　数え方（DumpVerify.kt と同じ）
    行      コレクション ID ごと（パスの最後のコレクション ID）。
            ファイルにあるコレクション ID。
            ファイルの範囲がプロジェクトの時は、クラウドのルートコレクションも足す。
    クラウド  そのコレクション ID のコレクショングループの件数
    ファイル  ファイルの中の件数
    詳細では、ファイルのドキュメントをパスでクラウドから読み、比べる。
    差分ドキュメント数（その側のドキュメントのうち、相手の側と一致しないもの）
      ファイル    ファイルにあってクラウドに無い数 + 中身が違う数
      クラウド    クラウドの件数 − 両方にあった数 + 中身が違う数
    差の絶対値ではなく、側ごとに出す。中身が違うドキュメントは、両方の側に数える。

＊　表示
    件数まで。ドキュメントの行は出さない。
    セルは、詳細なら「ドキュメント数 / 差分ドキュメント数」、簡易なら「ドキュメント数」。
    表の下に「＊詳細検証：ドキュメント数 / 差分ドキュメント数」（簡易は「＊簡易検証：ドキュメント数」）と
    「＊クラウドにだけあるコレクション / ドキュメントは、実行しても消えません。」を出す。
    見出しは「クラウド」「ファイル」。行はコレクション ID で揃え、片側に無い時は空欄。
    コレクションが片方にしか無い行、ドキュメント ID や中身が違う行は、背景を赤（dangerBg）にする。
    文字色は変えない。

    例
                クラウド         ファイル
    Group       280  20赤        310  50赤
    Member      9000 200赤       9600 600赤
    Post        10500            10500
    Inquiry     300（名が赤）     （空）
    Company     （空）            400（名が赤）

＊　クラウドにだけあるコレクション / ドキュメントは、実行しても消えない。



================================================================================
作り方
================================================================================


＊　書き込みは v1 クライアントの batchWrite を使う
    batch は全部成功か全部失敗なので、1 件が断られるとバッチ全体が失敗する。
    batchWrite は 1 件ずつ成否が返る。値は型を明示して書く（「整数と小数の区別」）。
    追記    currentDocument: { exists: false } を付けて update。
            code=6（ALREADY_EXISTS）は飛ばした件数。それ以外の失敗は書けなかった件数
    上書き  currentDocument を付けずに update（ドキュメントを丸ごと置き換える）

＊　同じパスの 2 回目以降
    書いたパスを覚えておき、2 回目以降を見分ける。持つのはパスだけで、中身は持たない。

＊　インポートの順番
    パスの深さで並べ替えない（今の sortByPath はやめる）。
    Firestore は、親ドキュメントが無くても子を書ける。ファイルを先頭から順に書く。

＊　公式ダンプのエクスポート
    LevelDB ログ（leveldb_log.ts の writeLeveldbRecords）を、全件を受け取る形から、
    1 件ずつファイルへ書き足す形にする。



================================================================================
値
================================================================================


＊　null のフィールドを、公式ダンプのエクスポートで落とさない
    document_to_entity.ts の encodeValue が null の時に null を返し、
    encodeProperty がそれを「書かない」と扱うので、null のフィールドがダンプから消える。
    null は、中身の無い値（field 5 が空）として書く。
    読む側（entity_to_document.ts の propertyValue）は、中身の無い値を null に戻す。

＊　空の配列（公式ダンプのエクスポート）
    配列は要素ごとに展開して書くので、空の配列はプロパティが 1 つも出ず、フィールドが消える。
    配列の中の配列も書かない。
    モバイル版（EntityEncoder.kt）も同じ。今のままでよい。

＊　リファレンス
    宛先プロジェクトのドキュメントを指すように書く（公式ダンプ・JSON とも）。
    今の公式ダンプのインポートは、読む時に path だけを取り出し（entity_to_document.ts）、
    書く時に宛先プロジェクトの doc(path) にする（serialize.ts の deserializeFirestoreValue）ので、
    書き込みは宛先を指している。
    検証で値を比べる時も、宛先プロジェクトに書き換えた後の値で比べる。



================================================================================
整数と小数の区別
================================================================================


＊　モバイル版の仕様
    30 は整数、1.0 は小数。見た目から型を推測しない（002_007）。
    2^53 を超える整数も、丸めずにそのまま扱う。

＊　通常の API（firebase-admin、@google-cloud/firestore 7.11.6）の制約
    書く時    JS の数値は、整数で表せる値なら整数（integerValue）として送られる
              （serializer.js の Number.isSafeInteger）。
              小数の 1.0 を書くと、整数の 1 になる。通常の API で 1.0 を小数のまま書く方法は無い。
    読む時    useBigInt なしでは、整数の 1 と小数の 1.0 が、どちらも JS の 1 になる。
              2^53 を超える整数は丸まる。
    JSON      JSON.parse / JSON.stringify では 1 と 1.0 の区別が消える。

    今の公式ダンプのインポートも同じで、小数の 1.0 は整数になって書かれている。

＊　読む
    useBigInt: true の Firestore の接続で読む。整数は BigInt、小数は number で返る。
    マップ・配列の中も同じ。
    インポート / エクスポート専用の接続にする。アプリ全体の接続（クエリ・エディタ等）は変えない。

＊　書く
    v1 クライアント（@google-cloud/firestore の v1.FirestoreClient）の batchWrite で、
    型を明示して書く。
      整数    { integerValue: "9007199254740993" }（文字列で渡す）
      小数    { doubleValue: 1 }
      マップ・配列の中も、同じように型を明示する。

＊　JSON
    読む    JSON.parse の reviver の 3 つ目の引数（context.source）で、元の文字列を受け取る。
            "1" は整数、"1.0" / "1e3" 等は小数。整数は元の文字列から BigInt にする。
    書く    JSON.rawJSON で、小数の 1.0 は "1.0"、BigInt は桁をそのまま書く。

＊　確かめたこと（Emulator、scripts/exp_number_type.mjs）
    v1 で書く      doubleValue 1 は小数 1.0 のまま残る。integerValue "9007199254740993" は桁どおり残る。
                   マップ・配列の中も型が残る。NaN / 無限大も残る。
    通常の API で書く  number 1 は整数、1.5 は小数、BigInt は整数になる。
    useBigInt で読む   整数は BigInt、小数は number。マップ・配列の中も同じ。
    batchWrite      1 件ずつ成否が返る。
                    既にあるドキュメントへの追記は code=6（ALREADY_EXISTS）。
                    無いドキュメントへの追記と、上書きは code=0。
                    Emulator では、batchWrite に管理者のヘッダー（Authorization: Bearer owner）が要る。
    JSON（Electron 33.4.11、V8 13.0）
                    reviver の context.source で "1" と "1.0" を見分けられる。
                    "9007199254740993" も元の文字列で受け取れる。
                    JSON.rawJSON("1.0") は 1.0 と書き出される。

＊　確かめたこと（本番、テスト用プロジェクト mintfarm-b62db、scripts/exp_number_type_prod.mjs）
    v1 クライアントを、サービスアカウントの JSON で繋ぐ。
      new v1({ credentials: { client_email, private_key }, projectId })
    通信は gRPC と REST の両方で試し、結果は同じ。
      REST  new v1({ ...同じ, fallback: 'rest' }, require('google-gax/build/src/fallback'))
            （アプリの preferRest: true と同じ方式）
    v1 で書く      doubleValue 1 は小数 1.0 のまま残る。integerValue "9007199254740993" は桁どおり残る。
                   マップ・配列の中も型が残る。NaN も残る。
    useBigInt で読む   整数は BigInt、小数は number。マップ・配列の中も同じ。
                   （preferRest: true の通常の API で読んだ）
    batchWrite      既にあるドキュメントへの追記は code=6（ALREADY_EXISTS）。他の書き込みは道連れにならない。
                    無いドキュメントへの追記は code=0。
                    上書きは code=0 で、ドキュメントが置き換わる。
    書き込みは _firemint_exp の下だけ。最後に全部消した（残り 0 件）。

デスクトップ版だけにあるもの
================================================================================


残す。

＊　Emulator へのインポート・エクスポート
    Emulator の画面にも、クラウドの画面と同じに、追記 / 上書き・簡易検証 / 詳細検証・インポート実行がある。
    インポート先は選ぶ。先頭は「新規 ID」、その下に、データのある（ルートのコレクションがある）Emulator のプロジェクトが並ぶ。
    空のプロジェクトは出さない（空は存在しない扱い）。
      新規 ID  ID を入れる。英小文字・数字・ハイフン。
               最初の値は demo-import-1（使っている番号は飛ばす）。ファイルを選ぶと、自分で変えていなければエクスポート元になる。
               その ID のプロジェクトを Emulator に作って書く。もうある ID なら、そこへ書く。
      インポート先はファイルの前に出す（クラウドと同じ順）。
      ファイルを選んだ時、インポート先をまだ選んでいなければ、エクスポート元と同じ ID のプロジェクト、無ければ新規 ID になる。
    選んだプロジェクトにそのまま書く。クラウドの画面で Emulator のプロジェクトを選んだ時も同じ。
    エクスポート元と違うプロジェクトに入れる時は、クラウドと同じ確認が出る。
    新規 ID の検証は、Emulator 側が（なし）になる。
    エクスポートも、プロジェクトを選ぶ（データのある Emulator のプロジェクトだけ。最初は左の一覧で選んでいるもの、データが無ければ先頭）。
    クラウドの画面でも、Collection / Group / Project のどれでもプロジェクトを選ぶ。
    Emulator のプロジェクト ID は workspace に保持する（ID と Emulator のホスト）。
      アプリ立ち上げ直後  workspace の Emulator の ID を 1 つずつ調べる。
                          ルートのコレクションが無い → workspace から破棄する。
                          ある → ツリーに出す。
                          Emulator が答えない（動いていない）→ 調べられないので、ツリーに出さずに残す。
      インポートで新規 ID  workspace に足す。ほかの行（emulator など）は変えない。
      見つけた Emulator    アプリ立ち上げ直後に見つけた Emulator は、立ち上げた時の ID（Emulator が残すファイルの名前）でつなぐ。
                          空でも workspace に入れてツリーに出す（Emulator の画面は、この行を選んで開く）。
                          ID が分からない時は、つながない。
      順番                1. workspace の Emulator の ID を全部調べ、空なら破棄する。
                          2. その後で、見つけた Emulator の ID をつなぐ（空でも出す）。
                          同じ ID が両方に当たる時は、1 で破棄されて 2 で入り直すので、ツリーに出る。
      削除                Emulator の画面の削除で、workspace からも消える。

＊　フォルダの読み込み
    zip の他に、フォルダ（コンソール / gcloud / Emulator の出力）を選べる。

＊　インポートの範囲
    インポートは「プロジェクト」に固定（imp_exp.ts の applyImpExpIntent）。

テスト
================================================================================


■ は確かめた。□ はまだ。
画面のテストは Emulator（npm run emulators）と、テスト用プロジェクト mintfarm-b62db で行う。


＊　部品（Emulator、スクリプト）

  ■ JSON の書き読み
      1.0 は "1.0"、整数は "1"、大きな整数（9007199254740993）は桁どおり書かれる。
      NaN / 無限大は {"__firemint_type":"double",...} で書かれる。
      読み戻すと、型ごと同じになる（1.0 は小数、1 は整数、ナノ秒も残る）。

  ■ 公式ダンプのエンティティの書き読み
      null・負の整数・1.0 を含めて、読み戻すと同じになる。
      キーのプロジェクト（s~{projectId}）が読める。

  ■ ファイルの読み込み
      JSON  形式・エクスポート元・範囲が読める。読めない行は bad として数えられる。
      公式ダンプ（フォルダ）  形式・エクスポート元・範囲（all_kinds はプロジェクト）が読める。

  ■ 追記
      1 回目  書いた 3 / 飛ばした 1（同じパス）/ 書けなかった 1（読めない行）
      クラウドの値が型どおり（1.0 は小数、大きな整数は桁どおり）。
      リファレンスは宛先プロジェクトのドキュメントを指す。
      2 回目  書いた 0 / 飛ばした 4。既にあるドキュメントは変わらない。

  ■ 上書き
      書いた 3 / 飛ばした 1（同じパス）。
      クラウドにだけあるフィールドが消え、1.0 は小数のまま。


＊　エクスポート（画面）

  ■ 形式（公式ダンプ / JSON）を選べる。範囲（コレクション / グループ / プロジェクト）は形式で変わらない。

  ■ 保存先
      選ばない時は Documents/FireMint に、自動の名前（export-{範囲}-{名前}-{時刻}.zip / .jsonl）で保存される。
      画面の保存先に、Documents/FireMint のフォルダが出る。

  ■ 保存先を選ぶ
      「保存先を選ぶ…」で、場所とファイル名を選ぶダイアログが出る。ボタンは「選択」。
      最初の値は、前に選んだフォルダ（初めては Documents/FireMint）と自動の名前。
      場所とファイル名を変えて「選択」を押すと、画面の保存先にそのパスが出る（まだ保存しない）。
      エクスポートすると、そのとおりに保存される。
      同じ名前のファイルを選ぶと、OS の上書き確認が出る。
      形式を変えると、選んだファイル名の拡張子も変わる。
      エクスポートが終わった後も、選んだフォルダが残る。ファイル名は自動の名前に戻る。

  ■ JSON のファイル
      テキストエディタで開いて、1 行目が見出し、2 行目から 1 行 1 ドキュメントになっている。
      タイムスタンプ・位置情報・リファレンス・バイト列が __firemint_type で出ている。
      1.0 は "1.0" で出ている。

  ■ 同じ範囲の公式ダンプと JSON で、件数が同じ。

  ■ 公式ダンプで null のフィールドが落ちない
      null のフィールドを持つドキュメントを出し、入れ直して、null のフィールドが残っている。

  ■ 書きかけのファイル
      途中で中止すると、保存先にファイルが残らない（.part も残らない）。
      中身が無い範囲を出すと、エラーになり、ファイルが残らない。

  ■ Emulator の画面からのエクスポート
      クラウドの画面と同じ流れになる。
      画面に保存先が出る。選ばない時は Documents/FireMint に、自動の名前で保存される。
      「保存先を選ぶ…」で場所とファイル名を選ぶ（ボタンは「選択」。押した時は保存しない）。
      「エクスポート」を押した時に保存が始まる。選んだ場所に公式ダンプが保存される。
      エクスポートが終わった後も、選んだフォルダが残る。ファイル名は自動の名前に戻る。

  ■ Emulator のプロジェクトの保持
      新規 ID でインポートすると、行が足される。立ち上げ時の行は消えない。
      アプリを開き直すと、データのある ID が全部ツリーに出る。
      Emulator を立ち上げ直してからアプリを開くと、空になった ID は出ず、workspace からも消えている。
      Emulator を止めたままアプリを開くと、Emulator の ID はツリーに出ない。立ち上げてから開き直すと出る。
      Emulator を立ち上げた直後（空）にアプリを開くと、「firemint-e801f emulator」の行が出る（emulator の行は出ない）。
      その行を選ぶと、Emulator の画面が開ける。
      新規 ID で作った ID は、空になった後にアプリを開き直すと出ない。
  □ エクスポートのプロジェクトを選ぶ
      Emulator の画面  「プロジェクト」に、データのある Emulator のプロジェクトだけが並ぶ（空の行は出ない）。最初は左の一覧で選んでいるもの
                       （空・Emulator でなければ先頭）。Collection / Group / Project のどれでも出る。
                       データのあるプロジェクトが無い時は「データのあるプロジェクトがありません」と出る。
      クラウドの画面   Project の時も「プロジェクト」が出る。変えると、ルートの一覧がそのプロジェクトのものになり、全部選ばれる。
      選んだプロジェクトから出る。


＊　インポート（画面）

  ■ ファイルを選ぶ
      .zip / .jsonl / フォルダを選べる。
      選ぶと、形式とエクスポート元が表示される。
      見出しが無い・kind や version が違う・空のファイルは、選んだ時点でエラーになる。

  ■ 簡易検証
      コレクション ID ごとに、クラウドとファイルの件数が並ぶ。
      片側にしか無いコレクションの行と、ドキュメント数が違う行は、背景が赤になる。

  ■ 詳細検証
      セルが「ドキュメント数 / 差分ドキュメント数」になり、中身が違うドキュメントの数が出る。
      表の下に「＊詳細検証：ドキュメント数 / 差分ドキュメント数」が出る（簡易検証では「＊簡易検証：ドキュメント数」）。
      差分ドキュメント数が 0 でない行は、背景が赤になる。
      空のプロジェクトに入れた直後に詳細検証すると、全部の行で差分ドキュメント数が 0（赤なし）になる。

  ■ 実行前の確認
      検証せずに実行すると、警告が出る。警告のあと実行できる。
      エクスポート元と宛先が違うと、「このファイルは {元} からエクスポートしたものです。{宛先} に入れますか？」が出る。
      追記・上書きで、それぞれの確認文が出る。
      どれかでキャンセルすると、何も書かない。

  ■ 追記
      既にあるドキュメントが変わらない。無いドキュメントだけができる。
      結果に、書いた / 飛ばした / 書けなかった件数が出る。

  ■ 上書き
      既にあるドキュメントが、ファイルの中身とまったく同じになる（クラウドにだけあるフィールドが消える）。
      ファイルに無いドキュメントは残る。

  ■ 型ごと元どおりになる
      JSON でエクスポートしたファイルを空のプロジェクトに入れて、1 と 1.0・大きな整数・タイムスタンプ・
      位置情報・リファレンス・バイト列・null・NaN が元どおりになる。
      公式ダンプでも同じ。

  ■ 手で直した JSON
      値を変えた行、足した行が、そのとおりに入る。
      壊した行は書けなかった件数、同じパスの行は飛ばした件数として数えられる。

  ■ 途中で中止
      それまでに書いたドキュメントは残る。結果に、それまでの件数と止まった理由が出る。

  ■ read-only のプロジェクト
      検証はできる。実行はできない。

  ■ Emulator の画面からのインポート
      クラウドの画面と同じ流れになる。
      ファイル（ZIP / JSONL）かフォルダを選ぶと、形式・エクスポート元が出る。
      インポート先の先頭は「新規 ID」。その下に、データのある Emulator のプロジェクトだけが並ぶ。
      Emulator が空の時は、「新規 ID」だけになる。ID 欄には demo-import-1 が入っている。
      インポート先は、ファイルの指定より上にある。
      インポート先を選ばずにファイルを選ぶと、エクスポート元と同じ ID のプロジェクトが選ばれる。無ければ新規 ID で、ID 欄にエクスポート元が入る。
      先にインポート先を選んでおくと、ファイルを選んでも変わらない。
      新規 ID を書き換えると、その ID のプロジェクトが新しくでき、そこに入る。もうある ID なら、そこに入る。
      既にあるプロジェクトを選ぶと、そのプロジェクトに入る。エクスポート元と違うと、確認が出る。
      追記 / 上書きを選べる。
      簡易検証 / 詳細検証で、コレクション ID ごとに Emulator とファイルの件数が並ぶ（ボタンの下に出る）。
      「インポート実行」を押した時に、確認のあと書き始める。進捗とログは下に出る。
      .jsonl も入れられる。


＊　認証

  ■ サービスアカウントの JSON で繋いだ本番（mintfarm-b62db）に、v1 で書ける（実験、exp_number_type_prod.mjs）。

  ■ サービスアカウントの JSON で繋いだプロジェクトで、画面からインポートできる。

  ■ Google ログイン（OAuth）で繋いだプロジェクトで、画面からインポートできる（v1 の書き込み）。
